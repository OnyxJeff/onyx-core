# ONYX CORE v0.3.0 — deployment and rollback plan (DRAFT)

**Status:** Not approved for production. This document is for the controlled rollout after cross-platform tests, storage growth checks and security review.

## Existing production baseline
- Receiver: systemd `onyxcore-receiver.service` on `svr-onyxcore`.
- Script: `/opt/onyxcore/receiver.py`, existing `--state-file /var/lib/onyxcore/latest-snapshot.json`.
- TCP 8765 bound to the Pi's verified USB IPv4, not the LAN.
- Token: `/etc/onyxcore/receiver.env`, never print/copy into logs or Git.
- Windows SQUALL scheduled collector sends every 30 seconds.
- USB is also the Pi's power source: **do not physically disconnect the cable to test network recovery**.

## Release gates
1. Windows and original Pi Zero ARMv6 entire test suite pass at the same commit.
2. Confirm the SQLite acceptance watermark survives history rollover, empty history, reboot and replay.
3. Measure multiple retention windows / database free page reuse and check actual process RSS.
4. Recheck dashboard auth, localhost test, HTML security headers, token handling, and no LAN exposure.
5. Snapshot current production receiver script, installed service unit and latest snapshot before modifying anything.
6. Rehearse a rollback, including the possibility that telemetry was accepted by v0.3 since the backup.

## Proposed controlled migration (not commands to execute yet)
- Keep the Windows collector running until the scheduled maintenance interval; take a consistent snapshot/backup.
- Record current `systemctl cat onyxcore-receiver.service`, service environment file metadata (not its contents), bind address, and files' ownership/permissions.
- Stop *only* the receiver service. Stage tested Python modules and dashboard in `/opt/onyxcore`, preserving a v0.2 copy outside the Git repo.
- Use `--history-file /var/lib/onyxcore/telemetry.db` to enable SQLite; retain the existing state-file path and root-protected token.
- On first SQLite creation, import the validated v0.2 snapshot to preserve the replay boundary. A database that already exists must never import stale JSON as authoritative.
- Restart the receiver and confirm binding, healthy status, and authenticated writes from SQUALL, fresh JSON and history rows.
- Validate CPU/RAM overhead, bounded file growth, journal cleanup, dashboard authentication and access through USB.
- Keep a recovery plan and avoid announcing v0.3.0 until tested deployment and rollback.

## Rollback principle
- Stop the v0.3 receiver, preserve `telemetry.db` and its latest committed **acceptance watermark** as forensic/restore data.
- Ensure the compatibility JSON cache reflects the most recently accepted SQLite sample before returning to v0.2; do **not** blindly restore an older JSON backup or older sequences can be accepted.
- Restore the saved v0.2 script and original service arguments and restart.
- Confirm the collector's current session continues and duplicate/replay protection is preserved.
- If the JSON cache failed, repair it from the SQLite watermark using a carefully reviewed, offline exporter before starting v0.2. Do not overwrite a newer JSON with an older snapshot.
- Never delete the SQLite database as part of a rollback. Schedule follow-up reconciliation separately.

## Current known limitations
- A SQLite database is bound by logical seven-day retention; deleted pages can remain allocated. Growth over multiple retention windows has not yet been characterized.
- The dashboard is served over HTTP on a private USB link; a bearer token is entered in browser memory. Evaluate browser-side attack surface and reserve a separate read-only token if needed.
- This project is not yet long-term endurance tested and does not provide a remote power-on service.
