# ONYX CORE v0.4.0 — release readiness, deployment and rollback

**Status:** Pre-deployment runbook — **not authorization to deploy**, merge or tag. Tracks [Issue #9](https://github.com/OnyxJeff/onyx-core/issues/9). Production remains v0.3.0 until explicit approval.

## Scope / release contract

v0.4.0 adds a pure UTC freshness evaluator, a read-only SQLite-watermark health query, authenticated `GET /api/v1/health` and local dashboard state/transition display. Defaults: healthy age <=90s; warning >90s to <=180s; critical >180s. No data is not necessarily an incident; the Windows collector launches after login. Receiver-unreachable is browser-local only when the dashboard is open. No new daemon, port, external notification service or Python runtime dependency.

**Only deploy these five Pi application files from the reviewed feature commit:**
- `pi/services/receiver/receiver.py`
- `pi/services/receiver/integrated_store.py`
- `pi/services/receiver/health.py` **(new)**
- `pi/services/receiver/dashboard.html`
- `pi/services/receiver/history.py` **existing dependency: do not replace; inspect its current installation**

Actual changed source files are the first four; `history.py` is listed for compatibility inspection, not as an install/update target. Do **not** install test files into `/opt/onyxcore`, replace the systemd unit, launcher, environment, or change networking. The production release remains bound only to the existing USB IP and port 8765. No new database schema or intentional state migration is introduced.

## Stage and backup procedure — **run only after release approval**

The commands below are a **reviewable plan**, not steps already performed. Use the approved merged revision, never an unreviewed working tree. Run on Pi as an administrator; verify each source path before copying.

1. Confirm service binding, source hashes, directory owner/mode, current `sqlite3` `quick_check`, network state, collector delivery and that enough storage exists. Record process RSS with `ps -o pid,rss,cmd -p "$(systemctl show -p MainPID --value onyxcore-receiver.service)"`.
2. Create a root-owned `0700` backup directory with a UTC timestamp beneath `/var/backups/onyxcore/pre-v0.4.0/`. Preserve *all* four current application files including `receiver.py`, `integrated_store.py`, `dashboard.html` and `history.py`, plus the launcher and systemd unit. Check whether `health.py` existed before deployment; normally it did not.
3. Stage **only** approved `receiver.py`, `integrated_store.py`, `health.py`, `dashboard.html` outside `/opt/onyxcore`, compare SHA-256 digests with the approved revision, check `python3 -m py_compile` (outside production or with controlled `PYTHONPYCACHEPREFIX`), and verify no unexpected file differences.
4. Schedule a brief collector retry window; **stop only** `onyxcore-receiver.service`. Wait until port 8765 closes. Record the final committed SQLite watermark/sample count, not just an earlier observation.
5. With the receiver stopped, take a **consistent SQLite backup** using Python `sqlite3.Connection.backup()` or SQLite's approved backup mechanism into a protected `0600` file. Preserve the live database **in place**, and retain the latest JSON cache separately for forensic/recovery reference. Do not copy a live SQLite file with arbitrary `cp` while writes are ongoing.
6. Install the four staged files into `/opt/onyxcore` as `root:root 0644`; verify SHA-256 after copying. Do not replace `history.py`, `launch-receiver.sh`, `receiver.env`, the existing service unit or SQLite files.
7. Start the existing service and verify listener remains at the private USB IP `192.168.137.167:8765`. Confirm the running process uses the existing launcher and `/var/lib/onyxcore/telemetry.db`. Check `journalctl -u onyxcore-receiver.service` for startup failures **without exposing tokens**.
8. Verify `/healthz` (process only); unauthenticated `/api/v1/health` returns 401; authenticated `/api/v1/health` returns current state and `Cache-Control: no-store`. Use the existing production token only **locally**, never copy its value into a ticket/chat or Git.
9. Verify `GET /api/v1/history` and `/api/v1/latest` remain authenticated, dashboard loads, and fresh Windows collector submissions continue. Verify the SQLite sample count grows, `PRAGMA quick_check=ok`, and committed `acceptance_watermark` is not reset or older than the final pre-stop boundary. Take a resource snapshot (RSS, CPU and storage).
10. Observe at least several normal collector cycles plus a controlled receiver restart; avoid rebooting the entire PC/Pi or altering working USB/ICS networking just to validate this release.

**Stop/go rule:** if any required check fails, halt the deployment and follow rollback below. Do not wipe state, reset session IDs, change the Windows collector configuration, regenerate the production token, or replay old snapshots to get a green dashboard.

## Rollback to v0.3.0 — **preserve authoritative SQLite**

**Critical:** Restore *code*, not older *state*. A backup of `telemetry.db` and `latest-snapshot.json` is disaster-recovery evidence, **not** a routine downgrade artifact. New writes may have been accepted after deployment; overwriting them with a pre-v0.4 backup can lose samples and move the replay boundary backwards.

1. Stop only `onyxcore-receiver.service`; verify port 8765 is closed.
2. Preserve the **current** SQLite DB and latest cache as protected incident evidence. Record `PRAGMA quick_check` and current watermark if possible.
3. Restore the backed-up `receiver.py`, `integrated_store.py`, `dashboard.html` and any other **preexisting changed application files**, preserving `root:root 0644`. Remove newly added `/opt/onyxcore/health.py` **only if** it was absent in the recorded baseline and no other component depends on it. Do not alter the existing `history.py`, launcher, service or protected token environment.
4. Leave the live `telemetry.db` in place. Only consider a database restore for independently verified corruption after separately preserving the latest state and choosing an explicit data-loss recovery plan.
5. Restart the original service, verify USB-only binding and authenticated telemetry/history/dashboard. Recheck SQLite integrity and continuity of the authoritative acceptance watermark; confirm new collector samples are accepted.
6. Document failure symptoms, hashes, timestamps and corrective action in Issue #9. Do not tag v0.4.0 until the rollback/deployment gates are met.

## Security and known limitations

- Same bearer token currently authorizes both telemetry writes and read endpoints. v0.4.0 does **not** introduce a read-only credential. Keep it on the private USB link; do not port-forward or share dashboards publicly.
- `--allow-loopback-test` is an explicit **test-only** bind opt-in. It is never passed by the production systemd launcher and is not a general public-interface allowance.
- No alerts are sent when the dashboard is closed; browser cannot infer that a receiver is down unless a polling page is already open.
- `no_data` and stale telemetry can be expected before Windows logon. WARNING/CRITICAL indicate sample age, not confirmed root cause.
- USB networking and Windows ICS recovery are documented separately in [the environment-specific troubleshooting runbook](troubleshooting/usb-gadget-networking.md); do not change them as part of application release.
- Long-term microSD write endurance, power-loss integrity and unattended pre-logon Windows ICS recovery are not established by v0.4.0 tests.
