# ONYX CORE v0.3.0 — deployment, validation and rollback

**Status:** Deployed and verified on original Raspberry Pi Zero (ARMv6), November 1, 2026. Preserve the v0.2.0 rollback backup while observing the upgrade.

## Release features
- Opt-in SQLite-backed telemetry with seven-day retention and up to 500 history rows per API request.
- Atomic accepted-sample and replay-protection watermark transactions, independent of pruned history.
- Authenticated `GET /api/v1/history?limit=120` and `GET /api/v1/latest` endpoints.
- Self-contained dashboard at `http://192.168.137.167:8765/dashboard` (use your Pi's actual USB IP), requiring the existing receiver bearer token.
- JSON latest-snapshot compatibility cache is repaired from the durable watermark when restarting.
- Standard library only; no extra Python dependencies.

## Validated release evidence
- 34/34 unit/integration tests passed on Windows (3.566 seconds) and Pi Zero ARMv6 (4.300 seconds).
- 20,160 simulated samples occupied ~3.285 MiB; 500-row query completed in ~55.925 ms on Pi.
- 21-day simulated retention: Day 7 3,500 samples / 610,304 bytes; Days 14 and 21 ~3,501 samples / 626,688 bytes. Page reuse observed.
- Live receiver service active, SQLite integrity `PRAGMA quick_check` = `ok`; sample count advancing and JSON cache equal to durable acceptance watermark.
- Live SQUALL browser dashboard authenticated and showed LIVE status, two charts, CPU/memory/uptime and local timestamps. Pi receiver ~20,068 KiB RSS.
- Does not establish unlimited microSD endurance, tested reboot behavior or guaranteed availability. Continue to monitor.

- SQLite: `/var/lib/onyxcore/telemetry.db` (mode 0600)

- Previous release backup: `/var/backups/onyxcore/pre-v0.3.0/` (directory mode 0700)

## Existing launcher behavior
The service is started as the `onyxcore` user by its systemd launcher, which discovers the Pi USB ICS address from `usb0` and executes the receiver with:
```text
--bind <Pi USB IPv4> --port 8765 --state-file /var/lib/onyxcore/latest-snapshot.json --history-file /var/lib/onyxcore/telemetry.db
```
The `--history-file` switch is opt-in; no history argument provides snapshot-only compatibility mode. Keep systemd protections `NoNewPrivileges=true`, `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`, `ReadWritePaths=/var/lib/onyxcore`, and `UMask=0077`.

## Clean deployment / upgrade workflow
1. Run all tests on the source revision: `python3 -m unittest discover -s tests/services -p 'test_*.py' -v`.
2. Confirm the USB IP and running service, back up the old script, launcher, unit and latest snapshot in a root-only directory. Do not back up, display, or commit the token.
3. Stage the tested receiver, history, integrated store and HTML files in a root-owned directory, confirm source hashes/bytes and Python syntax.
4. Stop only `onyxcore-receiver.service`. Preserve the **final** pre-upgrade snapshot after the service stops. Leave the Windows collector active to retry.
5. Install the staged files into `/opt/onyxcore`, add `--history-file /var/lib/onyxcore/telemetry.db` to the launcher. Confirm with `sh -n`.
6. Start the service, allow it to initialize, then inspect `systemctl status`, journal, process argv and `telemetry.db`. Do not assume that a successful `systemctl start` means DB initialization already completed.
7. Read SQLite with the `onyxcore` account (read-only); check `samples` rows, singleton `acceptance_watermark`, JSON cache equality and `PRAGMA quick_check` = `ok`.
8. Verify the browser dashboard via the private USB link; enter the receiver token locally without pasting it into tickets/chat.
9. Retain rollback artifacts until the new deployment has been observed under normal usage.

## Safe rollback to v0.2.0
**The backed-up JSON snapshot may be older than the last SQLite-committed sample. NEVER blindly overwrite the live JSON with the pre-upgrade copy.**

1. Stop the v0.3 receiver and preserve the SQLite DB intact. Keep a secured copy of its acceptance watermark.
2. Use the existing latest JSON only if it exactly matches the SQLite watermark. If it does not, reconstruct the snapshot *from the SQLite watermark*, including `schema_version: 1`, using a reviewed offline export; check owner `onyxcore` and mode `0600`.
3. Restore the backed-up v0.2 receiver Python script, launcher and unit; do not restore the outdated saved JSON snapshot.
4. `systemctl daemon-reload` if the service unit was restored; start the receiver and verify USB binding, collector acceptance and JSON updates.
5. Keep `telemetry.db` intact for later reactivation and troubleshooting. Do not merge histories casually or delete the DB.

## Known security and operational limitations
- The browser dashboard loads over HTTP on the *private USB ICS network*. The browser may say `Not secure`; do not expose this endpoint to LAN or internet. A localhost SSH tunnel is a safer option when desired.
- The same bearer token permits reading and writing telemetry. Future version may split read-only dashboard authorization.
- SQLite applies retention on accepted writes, not periodically when idle. Disk file size may not shrink after deleting rows; reuse of pages was verified.
- Database state is durable on successful commits, but long-term SD endurance and real power-failure recovery are not yet established.
- This release adds no remote PC power-control functionality.
