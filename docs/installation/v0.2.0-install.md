# ONYX CORE v0.2.0 — installed configuration and deployment

Status: **validated on SQUALL and svr-onyxcore; release pending review**. Tracking: [Issue #5](https://github.com/OnyxJeff/onyx-core/issues/5).

## Scope and prerequisites

Windows 11 SQUALL with Windows PowerShell 5.1 and a Raspberry Pi Zero Rev 1.3 ARMv6 on Raspberry Pi OS/Raspbian 13. v0.1.0 USB RNDIS gadget, Windows ICS, and `svr-onyxcore.local` resolution must already work. The Pi is powered by SQUALL USB: **never unplug or disable power to test network faults**. USB link uses Windows 192.168.137.1/24 and dynamically leased Pi 192.168.137.x; do not assume the observed 192.168.137.167 remains fixed. Do not expose TCP 8765 to LAN/WAN.

## Pi: receiver deployment (commands run on Pi)

From a checkout of this feature branch, copy `pi/services/receiver/receiver.py` to `/opt/onyxcore/receiver.py` and `pi/services/receiver/launch-receiver.sh` to `/opt/onyxcore/launch-receiver.sh`. Use root:root ownership and permissions 0644 for Python and 0755 for launcher. Ensure LF line endings (the repository has `.gitattributes` for `*.sh`). Install `pi/services/receiver/onyxcore-receiver.service` at `/etc/systemd/system/onyxcore-receiver.service` and `pi/services/receiver/90-onyxcore-receiver` at `/etc/NetworkManager/dispatcher.d/90-onyxcore-receiver` with root:root and 0755 for the dispatcher.

Create a locked-down `onyxcore` system account with no interactive login and `/var/lib/onyxcore` owned by `onyxcore:onyxcore`, permission 0750. Create `/etc/onyxcore` root-owned mode 0700, and `/etc/onyxcore/receiver.env` root-owned mode 0600. Set `ONYXCORE_TOKEN=<random secret of at least 32 characters>` in that environment file through a private editor; **never add the real token to Git or shared output**. Use a strong random token, not the placeholder. The service runs as `onyxcore`, discovers the current USB address, and binds only to that address.

After provisioning, use:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now onyxcore-receiver.service
systemctl is-active onyxcore-receiver.service
sudo ss -lntp | grep ':8765'
```

The receiver retries if USB DHCP is not yet available; the NetworkManager dispatcher restarts an active receiver if the USB address changes. An *actual* in-service DHCP reassignment remains untested. The snapshot is stored at `/var/lib/onyxcore/latest-snapshot.json`, written atomically as mode 0600. Use `sudo python3 -m json.tool /var/lib/onyxcore/latest-snapshot.json` only after receiving the first sample.

## Windows: secret and collector

Keep the checkout wherever desired, but keep `Launch-OnyxTelemetry.vbs` and `Send-OnyxTelemetry.ps1` in the **same folder**. The launcher resolves the collector relative to itself. Run `windows/collector/Save-OnyxToken.ps1` interactively **as the same Windows account that runs the task**, entering the Pi token securely at the prompt. DPAPI CurrentUser stores it at `%LOCALAPPDATA%\OnyxCore\collector-token.dpapi`. Do not put this token, a decrypted copy, or the Pi environment file in Git. Restrict file ACLs to the intended user, SYSTEM, and Administrators.

Example task creation in Windows PowerShell **as the intended logged-in account** (replace `$repo` with your actual repository location):

```powershell
$repo = 'D:\github_repos\onyx-core'
$name = 'ONYX CORE - Telemetry Collector'
$launcher = Join-Path $repo 'windows\collector\Launch-OnyxTelemetry.vbs'
$action = New-ScheduledTaskAction -Execute "$env:SystemRoot\System32\wscript.exe" -Argument ('"{0}"' -f $launcher)
$trigger = New-ScheduledTaskTrigger -AtLogOn -User "$env:USERDOMAIN\$env:USERNAME"
$principal = New-ScheduledTaskPrincipal -UserId "$env:USERDOMAIN\$env:USERNAME" -LogonType Interactive -RunLevel Limited
$settings = New-ScheduledTaskSettingsSet -MultipleInstances IgnoreNew -ExecutionTimeLimit ([timespan]::Zero) -AllowStartIfOnBatteries
Register-ScheduledTask -TaskName $name -Action $action -Trigger $trigger -Principal $principal -Settings $settings
```

If the task already exists, **edit rather than re-register**. The tested task uses an Interactive logon, limited privileges, one trigger at user logon, no execution time limit, and IgnoreNew duplicate task behavior. Windows collection is enabled **after sign-in**, not while at the login screen. Do not run as SYSTEM or S4U unless reworking user-scoped DPAPI storage.

The default launcher starts `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass`, `-UseSavedToken -IntervalSeconds 30 -Count 0`, with the window fully hidden. It waits for process termination and forwards its exit code to Task Scheduler. Changing the checkout path requires updating the task's **launcher path**, not its internal collector path. A running task uses the launcher version loaded at launch; stop/start after updates.

Collector logs are at `%LOCALAPPDATA%\OnyxCore\collector.log` (one prior log rotated around 1 MiB). Sample metrics: CPU load, memory use, uptime. No dashboard, historic sample database, alerts, or sensors beyond these metrics are included in v0.2.0.

## Check / recovery

```powershell
Get-ScheduledTask -TaskName 'ONYX CORE - Telemetry Collector' | Select-Object TaskName,State
Test-NetConnection svr-onyxcore.local -Port 8765
Get-Content "$env:LOCALAPPDATA\OnyxCore\collector.log" -Tail 12
```

On the Pi: `systemctl is-active onyxcore-receiver.service`, `sudo ss -lntp | grep ':8765'`, and inspect the latest snapshot with `sudo python3 -m json.tool /var/lib/onyxcore/latest-snapshot.json`. Stop only the Windows task with `Stop-ScheduledTask -TaskName 'ONYX CORE - Telemetry Collector'`; no USB unplugging necessary.

Limitations: plain HTTP bearer authentication on USB-only RNDIS, static source identifier SQUALL, latest snapshot only, no end-to-end TLS, no established long-term endurance benchmark, and untested real DHCP renumbering. See `docs/testing/v0.2.0-validation.md`.
