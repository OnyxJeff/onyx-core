## Safety and authority

`windows/monitoring/v080/OnyxOfflineAlertLifecycle.py` is a pure Python alert-state engine. Its CLI supports ONLY `--check-inert`; the library exposes `initial_state`, `validate_state`, `ingest_synthetic_batch`, and `acknowledge_synthetic` for offline tests. No network clients, notifier integrations, SMTP/webhooks, Task Scheduler, collector, SSH, ICS repair, v0.7 incident store/adapter, filesystem writes, or enrollment are imported or called. The code does not authenticate any Windows user, inspect real ACLs, or validate real consent. It is never a trusted alert-producing runtime component.

Its intake requires a bounded UTF-8 JSON envelope with **exact** keys `schema_version`, `source`, `provenance`, `reference_utc`, `events`; `source=OnyxV080M3SyntheticAlerts`, `provenance=SyntheticFixtureOnly`. Only 1–32 synthetic events per call, each at most 300 seconds older or five seconds newer than the supplied *synthetic* reference. Both the reference and events require offset-aware dates. Inputs refuse duplicate JSON keys, unknown fields, NaN/infinity, invalid UTF-8, oversized payloads, and reordered events. Input validation is not authentication or origin attestation.

## v0.7.0 event compatibility

M3 uses the **shape** produced by v0.7.0's pure `OnyxIncidentState._event`: `schema_version`, `event_id`, `event_type`, `timestamp_utc`, `incident_id`, `from_phase`, `to_phase`, `connectivity_decision`, `repair_action`. Event IDs must match the v0.7 deterministic `evt-` + first 24 hex characters of SHA-256(`kind|timestamp_utc|incident_id-or-none`). Event types are `IncidentOpened`, `IncidentEscalated`, `IncidentRecovered`, `EvidenceIncomplete`, and `EvidenceRestored`. No repair claim is permitted. Event IDs and event-content digests provide **consistency checks only**; they do not prove a live observation, prevent a malicious fixture author from forging a value, or replace v0.7's reducer.

M3 validates phase and incident linkage (open → suspected/active; suspected → active; suspected/active → recovered; evidence transitions do not change incident phase). Evidence loss changes display to `Unknown` and cannot close or confirm recovery; evidence must be restored before new incident/escalation/recovery transitions. M3 consumes an `IncidentRecovered` transition **only if presented**; it cannot independently prove the two healthy cycles spaced 30–300 seconds apart that the v0.7 reducer requires to generate a genuine recovery. Therefore M3's outbound kind is intentionally `RecoveryCandidate`—not a production recovery assertion. The v0.7 reducer and M2C retain responsibility for that source-of-truth recovery rule.

## Deduplication and acknowledgements

`ingest_synthetic_batch` returns an **all-or-nothing** new deep-copied state, zero or more `proposed_intents`, and counts of newly processed vs exact replay-suppressed events. A replayed event with identical ID/content produces no new intent; same ID with changed content is refused. Unknown out-of-order events are refused. Separately, one intent per `(incident_id-or-none, event_type)` suppresses repetitive `EvidenceIncomplete` proposals for the same incident even if repeated loss/restoration events have distinct IDs. `EvidenceRestored` records evidence completion but creates no outbound notification intent.

All proposals are `simulation_only=true`, `delivery_permitted=false`. The overall outcome also sets `notification_enabled=false`, `runtime_enabled=false`, `live_probe_authorized=false`, `task_creation_authorized=false`, `store_modified=false`, and `repair_action=None`. The fixed in-memory 256-record event and intent ledgers refuse further events at capacity rather than evict an ID and permit accidental re-alerting. This is intentionally **not durable deduplication** after a restart; no state is stored. Durable alert journaling, crash replay, retention, and reliable notification transport need separately authorized milestones.

`acknowledge_synthetic` accepts only a bounded `synthetic:` actor, the exact open incident ID, and an offset-aware synthetic time at or after the last observed event when first recorded. The same actor and time replay idempotently; conflicting acknowledgements are refused. Acknowledgement neither resolves the incident nor hides evidence-loss status; it persists during incident escalation and is cleared only when the incident is recovered. A later event timestamp can exceed acknowledgement time without invalidating the earlier acknowledgement.
