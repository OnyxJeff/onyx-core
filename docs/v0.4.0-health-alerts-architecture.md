# ONYX CORE v0.4.0 — Health Monitoring & Local Alerts Architecture

**Status:** Design baseline only. All development must occur on `feature/v0.4.0-health-alerts`; production remains v0.3.0.

**Tracking:** https://github.com/OnyxJeff/onyx-core/issues/9

## Goals and constraints
Add an honest health signal for telemetry from SQUALL to ONYX CORE, with a practical dashboard alert and no new daemon or dependencies. Preserve Pi Zero ARMv6 memory/SD budget, v0.3.0 SQLite history and acceptance watermark, USB-only port 8765, existing bearer authentication, Windows collector schedule and the release's rollback backup.

## Proposed information flow
```text
SQUALL collector (about every 30 seconds)
   | POST /api/v1/telemetry, bearer auth
   v
Pi receiver -> IntegratedStore -> SQLite samples + acceptance_watermark
       |                                   |
       | <--- lightweight read-only health evaluator
       v
Authenticated GET /api/v1/health
       |
       v
Browser dashboard refresh (about every 30s)
  -> health indicator, last-seen age, local alert + recovery
  -> fetch error/timeout: mark receiver unreachable (only while browser is open)
```

## State model (first-pass contract)
Time values use UTC. Compute elapsed seconds from the **last accepted** watermark timestamp, not dashboard fetch time. No write is required when checking health.

| Condition | State | Meaning |
|---|---|---|
| No accepted watermark | `no_data` | Collector may not have logged in or run yet |
| Age 0..90 seconds | `healthy` | Telemetry within expected cadence |
| Age >90..180 seconds | `warning` | Several samples missed |
| Age >180 seconds | `critical` | Telemetry stale |
| Unexpected future timestamp/clock uncertainty | `unknown` | Do not incorrectly report healthy |
| SQLite/storage query fails | `degraded` or 503 | Can't establish source of truth |
| Browser cannot reach receiver | `receiver_unreachable` (client-only) | Local connection/service path unavailable |

The 90/180s boundaries are proposed defaults, not proof that SQUALL is malfunctioning: Windows collector is currently scheduled after user login. A stopped Windows session or powered-off PC will legitimately cause staleness. UI should communicate that distinction.

## Interfaces
Proposed `GET /api/v1/health` (bearer auth, `Cache-Control: no-store`):

```json
{
  "status": "warning",
  "reason": "telemetry_stale",
  "last_sample_utc": "2026-11-02T04:18:15Z",
  "age_seconds": 115,
  "warning_after_seconds": 90,
  "critical_after_seconds": 180
}
```

Treat unknown and storage failures as non-green. Do not send token/session ID in response. Retain `GET /healthz` as process reachability only. `GET /api/v1/history`, `GET /api/v1/latest` and `POST /api/v1/telemetry` remain compatible.

## Alert model
Local UI notifications only for v0.4.0, deduplicated by the current transition while the page is open; clearly mark recovery. Do not introduce a permanent notifications database or continuous writes. There is no claim of push notifications when the browser is closed. A separate monitor on SQUALL or another always-on host would be needed to alert when the receiver itself is unreachable while no browser is open.

## Test plan and deployment gates
- Pure evaluator tests with injected now for exact thresholds (0, 90, 91, 180, 181 seconds), no_data, clock anomalies, and transitions.
- HTTP tests for 401/200/503, no-store, and non-regression of existing APIs.
- UI tests for healthy/warning/critical, reconnect, stale vs unreachable, and token never persisted.
- Windows and Pi Zero ARMv6 full test suite before any production changes.
- Isolated development server on alternate port; no production DB or credentials.
- Measure process RSS and SQLite read overhead; do not add resource-heavy polling or packages.
- If a planned deployment is approved, preserve existing v0.3.0 files and current SQLite acceptance watermark for rollback. Never restore an old snapshot over newer accepted data.

## Deferred
Outbound SMS/email/Discord alerts, independent receiver/service watchdogs, Windows Scheduled Task redesign, remote power control, external monitoring integrations, OS metrics, and generalized event retention. Scope may be reconsidered for future milestones, not silently added.
